# Техническая документация: Telegram-бот для закупок техники по Москве

Версия: 1.0
Назначение документа: полная спецификация для разработки в Cursor. Документ закрывает архитектуру, схему БД, API, бизнес-алгоритмы, LLM-контракты, безопасность, окружение и план фаз. Разработчик/агент в Cursor должен быть в состоянии реализовать проект, используя только этот документ + исходный ТЗ.

Источник требований: `TZ-na-sozdanie-Telegram-bota-dlia-zakupok-po-Moskve.md` (приложен отдельно). Везде ниже пункты ТЗ помечены как `[ТЗ §N]`.

---

## 1. Цель и границы системы

Система заменяет ручную работу менеджера по закупкам: сбор прайсов ~10 поставщиков, сравнение цен, формирование прайса компании с наценкой, переписку с поставщиками, торг, повторную проверку цены, хранение истории для контроля и анализа `[ТЗ §1-7]`.

Жёсткое ограничение бизнес-логики: система не сама решает о сделке, не выдумывает цены, не меняет модель/цвет без сотрудника, не давит и не грубит с поставщиками `[ТЗ §5]`. При низкой уверенности разбора текста — передаёт исходный текст человеку, а не догадку `[ТЗ §4]`.

Вне скоупа (везде далее): userbot / инициация диалога без `/start`, автоматическое подтверждение сделки, работа с прайсами не в текстовом виде (файлы/фото) — если не согласовано отдельно.

Роли компонентов:

| Слой | Отвечает за | Не отвечает за |
|---|---|---|
| Telegram webhook + APScheduler | Приём Telegram-обновлений, cron, единая точка входа, алерты об ошибках | Бизнес-правила, состояние заявок |
| Backend | State machine заявок, whitelist, идемпотентность, шаблоны, вызовы LLM, запись в БД, отправка в Telegram | Долгосрочное планирование задач (это делает APScheduler) |
| БД | История (п.7 ТЗ), кэш LLM-ответов, кэш отчётов | — |
| LLM | Text→JSON извлечение; JSON→текст оформление | Любые числа/решения, которых нет в БД |

## 5. Роли и права доступа

| Роль | Таблица | Условие появления | Права |
|---|---|---|---|
| Владелец (owner) | `owners` | `telegram_id` внесён вручную + пользователь один раз нажал `/start` в ЛС боту (`dm_ok=true`) | `/report`, `/stats`, `/menu` (админка), `/purge_request`, `/purge_old`, push-аналитика |
| Сотрудник (employee) | `employees` | добавлен владельцем через `/menu` → «Сотрудники» или вручную в БД | `/ask`, `/bargain`, `/recheck`, `/setprice`, `/deal`, `/cancel`, `/status` в клиентских группах; неактивный (`active=false`) — команды игнорируются |
| Поставщик (supplier) | `suppliers` | ссылка на бота → `/start` → `chat_id` вносится в таблицу | Только свободные ответы/reply в ЛС боту |
| Клиент | — | участник клиентской группы | Пишет обычный текст; бот на него не реагирует напрямую (Privacy Mode ON) |

Ограничение Telegram Bot API: бот не может писать пользователю в ЛС первым — обязателен `/start` от поставщика и от владельца до получения сообщений в ЛС. Групповая аналитика (в `analytics_chat_id`) не требует `/start`, так как бот уже добавлен в чат.

Privacy Mode бота: **Enabled** (по умолчанию). Бот в группах видит только команды (`/...`), reply на свои сообщения и упоминания — не весь поток сообщений клиентов.

## 6. Схема базы данных (PostgreSQL DDL)

```sql
CREATE TYPE request_status AS ENUM (
  'open', 'awaiting_answers', 'priced', 'bargaining',
  'needs_recheck', 'closed', 'cancelled'
);

CREATE TYPE quote_source AS ENUM ('regex', 'llm', 'manual');
CREATE TYPE deal_outcome AS ENUM ('won', 'lost', 'cancelled');
CREATE TYPE message_kind AS ENUM ('ask', 'bargain', 'recheck');

CREATE TABLE owners (
  id BIGSERIAL PRIMARY KEY,
  telegram_id BIGINT UNIQUE NOT NULL,
  name TEXT,
  dm_ok BOOLEAN NOT NULL DEFAULT false,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE employees (
  id BIGSERIAL PRIMARY KEY,
  telegram_id BIGINT UNIQUE NOT NULL,
  name TEXT,
  active BOOLEAN NOT NULL DEFAULT true,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE suppliers (
  id BIGSERIAL PRIMARY KEY,
  telegram_id BIGINT UNIQUE,
  name TEXT NOT NULL,
  active BOOLEAN NOT NULL DEFAULT true,
  dm_ok BOOLEAN NOT NULL DEFAULT false,
  price_channel_id BIGINT,              -- id канала поставщика в сервисе-парсере (NULL = прайс шлётся текстом в ЛС/чат, как раньше)
  price_channel_username TEXT,          -- @username канала поставщика, для читаемости в UI/логах
  last_price_sync_at TIMESTAMPTZ,       -- время последнего успешного забора постов из канала этого поставщика
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE client_groups (
  id BIGSERIAL PRIMARY KEY,
  chat_id BIGINT UNIQUE NOT NULL,
  title TEXT,
  active BOOLEAN NOT NULL DEFAULT true
);

CREATE TABLE requests (
  id BIGSERIAL PRIMARY KEY,
  group_chat_id BIGINT NOT NULL,
  employee_id BIGINT NOT NULL REFERENCES employees(id),
  source_text TEXT NOT NULL,
  normalized_json JSONB,
  status request_status NOT NULL DEFAULT 'open',
  recheck_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE messages_out (
  id BIGSERIAL PRIMARY KEY,
  request_id BIGINT REFERENCES requests(id),
  supplier_id BIGINT NOT NULL REFERENCES suppliers(id),
  tg_message_id BIGINT NOT NULL,
  chat_id BIGINT NOT NULL,
  text TEXT NOT NULL,
  kind message_kind NOT NULL,
  sent_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (chat_id, tg_message_id)
);

CREATE TABLE messages_in (
  id BIGSERIAL PRIMARY KEY,
  request_id BIGINT REFERENCES requests(id),
  supplier_id BIGINT NOT NULL REFERENCES suppliers(id),
  tg_message_id BIGINT NOT NULL,
  chat_id BIGINT NOT NULL,
  raw_text TEXT NOT NULL,
  received_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (chat_id, tg_message_id)
);

CREATE TABLE quotes (
  id BIGSERIAL PRIMARY KEY,
  request_id BIGINT NOT NULL REFERENCES requests(id),
  supplier_id BIGINT NOT NULL REFERENCES suppliers(id),
  price_initial NUMERIC(12,2),
  price_bargain NUMERIC(12,2),
  qty INT,
  available BOOLEAN,
  condition TEXT,
  source quote_source NOT NULL,
  confidence REAL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE deals (
  id BIGSERIAL PRIMARY KEY,
  request_id BIGINT NOT NULL REFERENCES requests(id),
  chosen_supplier_id BIGINT REFERENCES suppliers(id),
  final_price NUMERIC(12,2),
  outcome deal_outcome,
  closed_at TIMESTAMPTZ
);

CREATE TABLE raw_prices (
  id BIGSERIAL PRIMARY KEY,
  supplier_id BIGINT NOT NULL REFERENCES suppliers(id),
  text TEXT NOT NULL,
  content_hash TEXT NOT NULL UNIQUE,
  source TEXT NOT NULL DEFAULT 'manual_message',   -- 'manual_message' | 'channel_post'
  source_post_id BIGINT,          -- id поста в tg_parser.parser_posts, если source='channel_post'
  source_message_link TEXT,       -- ссылка на оригинальный пост в канале, для ручной проверки
  received_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE parsed_items (
  id BIGSERIAL PRIMARY KEY,
  raw_price_id BIGINT NOT NULL REFERENCES raw_prices(id),
  sku_key TEXT NOT NULL,          -- model|storage|color|region|sim
  model TEXT, storage TEXT, color TEXT, region TEXT, sim TEXT, condition TEXT,
  price NUMERIC(12,2) NOT NULL,
  currency TEXT NOT NULL DEFAULT 'RUB',
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE markup_rules (
  id BIGSERIAL PRIMARY KEY,
  category TEXT NOT NULL,          -- apple / samsung / playstation / *
  markup_fixed NUMERIC(12,2),
  markup_min NUMERIC(12,2),
  markup_max NUMERIC(12,2),
  active BOOLEAN NOT NULL DEFAULT true
);

CREATE TABLE price_list_drafts (
  id BIGSERIAL PRIMARY KEY,
  generated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  items JSONB NOT NULL,
  status TEXT NOT NULL DEFAULT 'pending', -- pending/approved/rejected
  approved_by BIGINT REFERENCES employees(id),          -- NULL если утвердил owner без карточки employee
  approved_by_telegram_id BIGINT,                        -- telegram_id нажавшего (owner или employee), audit
  approved_at TIMESTAMPTZ
);

CREATE TABLE parse_cache (
  id BIGSERIAL PRIMARY KEY,
  content_hash TEXT NOT NULL UNIQUE,
  kind TEXT NOT NULL,               -- price_list / supplier_reply / normalize_request
  result_json JSONB NOT NULL,
  model_used TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE report_cache (
  id BIGSERIAL PRIMARY KEY,
  period_key TEXT NOT NULL UNIQUE,  -- напр. 2026-07-15_day
  metrics_json JSONB NOT NULL,
  formatted_text TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE update_log (
  id BIGSERIAL PRIMARY KEY,
  tg_update_id BIGINT NOT NULL UNIQUE,
  processed_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

`sku_key` формируется строго как `model|storage|color|region|sim` — это ключ сравнения цен из `[ТЗ §1]`, разные версии товара никогда не смешиваются по этому ключу.

## 7. API контракт backend (webhook Telegram + ручные /jobs/*)

`/telegram/webhook` защищён `X-Telegram-Bot-Api-Secret-Token`, значение задаётся в `setWebhook`. Ручные `/jobs/*` защищены `X-Webhook-Secret` (`WEBHOOK_SECRET`). Несовпадение → 401, без обработки тела.

### 7.1 `POST /telegram/webhook`

Вход: полный объект Telegram Update от Telegram webhook.

Алгоритм диспетчеризации:

1. Идемпотентность: если `update_id` уже есть в `update_log` → вернуть `200 {"status":"duplicate"}` без побочных эффектов.
2. Определить тип источника:
   - `message.chat.type in ("group","supergroup")` и текст начинается с `/` → ветка сотрудника (раздел 9.1, 9.3–9.6).
   - `message.chat.type == "private"` и `from.id ∈ suppliers.telegram_id` → ветка поставщика (раздел 9.2).
   - `message.chat.type == "private"` и `from.id ∈ owners.telegram_id` и текст `/report`/`/stats`/`/purge_request`/`/purge_old` → ветка владельца (`owner_commands.py`: отчёты и purge).
   - `message.chat.type == "private"` и `from.id ∈ owners.telegram_id` и текст `/menu`/`/admin` или активный `admin_dialogs` → owner admin menu (`admin_menu.py`): поставщики, сотрудники, клиентские беседы, новые чаты, каналы прайсов; callback `purge_confirm`/`purge_cancel` для подтверждения hard-delete.
   - `message.chat.type == "private"` и `from.id ∈ employees.telegram_id` — разрешить те же команды, что в группе, если сотрудник пишет боту напрямую (опционально, зависит от ответа заказчика, см. раздел 12).
   - Всё остальное (клиент без команды, чужой id) → игнорировать, вернуть `200 {"status":"ignored"}`.
3. Записать `update_id` в `update_log`.
4. Вернуть `200`.

### 7.2 `POST /jobs/morning-price`

Тело: `{}`. Запускает алгоритм 9.5 (сбор → сравнение → наценка → черновик прайса на approve).

### 7.3 `POST /jobs/recheck-due`

Тело: `{}`. Находит все `requests` со `status='needs_recheck'` и `recheck_at <= now()`, выполняет 9.4 (шаг «отправка запроса поставщику»).

### 7.4 `POST /jobs/daily-report`

Тело: `{"period": "day" | "week"}`. Запускает 9.6.

### 7.5 `GET /health`

Без авторизации. Возвращает `{"status":"ok","db":"ok"}` для проверки живости из docker-compose healthcheck.

## 8. Контракты LLM (structured output)

LLM вызывается ровно в трёх случаях и никогда — для принятия решений или генерации цифр, которых нет в системе.

### 8.1 Нормализация запроса сотрудника (`normalize_request`)

Вызывается только если regex/словарь не смог однозначно выделить SKU-поля из текста сотрудника/клиента.

JSON Schema результата:

```json
{
  "type": "object",
  "properties": {
    "model": {"type": "string"},
    "storage": {"type": ["string","null"]},
    "color": {"type": ["string","null"]},
    "region": {"type": ["string","null"]},
    "sim": {"type": ["string","null"]},
    "qty": {"type": ["integer","null"]},
    "condition": {"type": ["string","null"]},
    "confidence": {"type": "number", "minimum": 0, "maximum": 1}
  },
  "required": ["model", "confidence"]
}
```

### 8.2 Парсинг прайса поставщика (`parse_price_list`)

```json
{
  "type": "object",
  "properties": {
    "items": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "model": {"type": "string"},
          "storage": {"type": ["string","null"]},
          "color": {"type": ["string","null"]},
          "region": {"type": ["string","null"]},
          "sim": {"type": ["string","null"]},
          "condition": {"type": ["string","null"]},
          "price": {"type": "number"},
          "currency": {"type": "string", "default": "RUB"},
          "confidence": {"type": "number", "minimum": 0, "maximum": 1}
        },
        "required": ["model", "price", "confidence"]
      }
    }
  },
  "required": ["items"]
}
```

### 8.3 Парсинг ответа поставщика (`parse_supplier_reply`)

```json
{
  "type": "object",
  "properties": {
    "available": {"type": ["boolean","null"]},
    "qty": {"type": ["integer","null"]},
    "price": {"type": ["number","null"]},
    "min_sale_price": {"type": ["number","null"]},
    "condition": {"type": ["string","null"]},
    "note": {"type": ["string","null"]},
    "confidence": {"type": "number", "minimum": 0, "maximum": 1}
  },
  "required": ["confidence"]
}
```

Правило: если `confidence < CONFIDENCE_THRESHOLD` (по умолчанию 0.75, настраивается в `.env`) — поля `price`/`qty` НЕ пишутся в `quotes`; сотруднику показывается только `raw_text` с меткой «распознавание неуверенное» `[ТЗ §4]`.

### 8.4 Форматирование отчёта (`format_report`)

Вход — JSON с готовыми метриками (посчитан кодом/SQL, не LLM). Выход — текст в Telegram HTML (`parse_mode=HTML`).

Жёсткое системное правило промпта: «Используй только числа из входного JSON. Ничего не досчитывай, не оценивай, не придумывай. Если поле null — пиши «н/д»."

Обязателен fallback без LLM (Jinja2-шаблон на тех же полях) — если LLM недоступен, отчёт всё равно отправляется.

### 8.5 Кэширование LLM-вызовов

Ключ кэша: `sha256(kind + normalized_input_text)`. Перед вызовом LLM — проверка `parse_cache`. При совпадении — 0 вызовов LLM. Это обязательное требование `[раздел «сокращение количества запросов» из истории проекта]`.

### 8.6 Безопасность LLM

- Только structured output / JSON mode, ответ валидируется по JSON Schema перед использованием; невалидный JSON → трактовать как `confidence=0`.
- В промпт для генерации сообщений поставщику (торг) никогда не подставляются цены других поставщиков `[ТЗ §5]`.
- LLM не имеет доступа к функции отправки сообщений — только возвращает текст/JSON, отправку выполняет backend после валидации.

## 9. Бизнес-алгоритмы

### 9.1 Запрос поставщикам (`request_service.create_request`)

```
ВХОД: сообщение в группе, text начинается с "/ask"
      from.id ∈ employees, employees.active = true

1. text_req = reply_to_message.text (если есть reply) + текст после "/ask"
   если пусто → ответить "Нужен текст запроса или reply на сообщение клиента"
2. regex/словарь → попытка выделить model/storage/color/qty
   если неуверенно → LLM normalize_request (8.1)
3. INSERT requests (group_chat_id, employee_id, source_text, normalized_json, status='open')
4. suppliers_active = SELECT * FROM suppliers WHERE active=true
   (опционально: сотрудник указывает конкретных поставщиков — см. раздел 12, вопрос уточнения)
5. ДЛЯ каждого supplier:
     text = render_template("ask", request_id, normalized_json)
     msg = telegram.send_message(supplier.telegram_id, text)
     INSERT messages_out (request_id, supplier_id, tg_message_id=msg.message_id,
                           chat_id=supplier.telegram_id, text, kind='ask')
6. UPDATE requests SET status='awaiting_answers'
7. Ответ в группу: "Запрос #{id} отправлен {N} поставщикам"
```

### 9.2 Ответ поставщика → группа (`supplier_messages.handle_reply`)

```
ВХОД: сообщение в ЛС боту, from.id ∈ suppliers.telegram_id

1. request_id:
   a. если message.reply_to_message существует и его текст содержит "#N" → N
   b. иначе: последний request со status IN ('awaiting_answers','bargaining','needs_recheck')
      у которого есть messages_out этому supplier
   c. если не найдено → ответить поставщику "Пожалуйста, ответьте на сообщение с номером заявки (#N)"
      и остановиться (raw всё равно НЕ сохраняется без привязки, либо сохраняется в messages_in
      с request_id=NULL для аудита — решение фиксируется в 6-й таблице)
2. INSERT messages_in (request_id, supplier_id, tg_message_id, chat_id, raw_text) — ВСЕГДА, независимо от парсинга
3. parsed = regex_parser.parse_supplier_reply(raw_text)
   если regex не дал price/qty → parsed = llm.parse_supplier_reply(raw_text)  (8.3, с кэшем 8.5)
4. если parsed.confidence >= CONFIDENCE_THRESHOLD:
     UPSERT quotes (request_id, supplier_id, price_initial=parsed.price, qty=parsed.qty,
                     available=parsed.available, condition=parsed.condition,
                     source='regex'|'llm', confidence=parsed.confidence)
     текст_в_группу = шаблон с "Наличие: ..., Цена: ..., Кол-во: ..." + оригинал
   иначе:
     текст_в_группу = "От: {supplier.name} · Заявка #{request_id}\n[распознавание неуверенное]\n{raw_text}"
5. telegram.send_message(request.group_chat_id, текст_в_группу)
```

### 9.3 Торг (`bargain_service.start_bargain`)

```
ВХОД: команда "/bargain {request_id} {target_price}" от employee в группе

1. Проверить request существует, status допускает торг
2. text = render_template("bargain", request_id, target_price)
   — шаблон НЕ содержит цен других поставщиков [ТЗ §5]
   — тон шаблона мягкий, без давления: "Коллеги, есть возможность сделать цену
     {target_price} ₽ по заявке #{request_id}?"
3. supplier = quotes.supplier_id с текущим лучшим предложением по этому request
   (или явно указанный сотрудником)
4. msg = telegram.send_message(supplier.telegram_id, text)
5. INSERT messages_out (kind='bargain', ...)
6. UPDATE requests SET status='bargaining'
7. Ответ поставщика обрабатывается тем же 9.2; при высокой confidence
   UPDATE quotes SET price_bargain = parsed.price
```

Бот сам не соглашается на новую цену и не подтверждает сделку — это делает сотрудник командой `/deal` (9.3.1).

**`/deal {request_id} {supplier_id} {final_price}`**:

```
1. INSERT deals (request_id, chosen_supplier_id=supplier_id, final_price, outcome='won', closed_at=now())
2. UPDATE requests SET status='closed'
3. Ответ в группу: "Заявка #{id} закрыта. Поставщик: {name}. Цена: {final_price} ₽"
```

### 9.4 Повторная проверка цены (`recheck_service`)

```
Команда сотрудника: "/recheck {request_id} [hours=2..5, default=3]"
1. UPDATE requests SET status='needs_recheck', recheck_at = now() + interval 'hours'

Периодически (APScheduler cron `*/15 * * * *` → direct вызов `run_recheck_due`):
2. SELECT * FROM requests WHERE status='needs_recheck' AND recheck_at <= now()
3. ДЛЯ каждой такой заявки:
     supplier = текущий выбранный поставщик по заявке
     text = render_template("recheck", request_id)
     telegram.send_message(supplier.telegram_id, text)
     INSERT messages_out (kind='recheck', ...)
     UPDATE requests SET recheck_at = NULL  (чтобы не слать повторно; статус остаётся needs_recheck
                                              до ответа, который обрабатывается через 9.2)
4. Если ответ поставщика содержит новую цену (price_initial != старая) →
     явно сообщить об изменении в группу: "Цена по заявке #{id} изменилась: было {old} ₽,
     стало {new} ₽" [ТЗ §6]
   Старая цена клиенту автоматически НЕ подтверждается — требуется явное подтверждение
   сотрудника (`/setprice` или ответ в чат).
```

### 9.5 Утренний прайс (`price_service.build_morning_price`)

Источники сырого текста прайса — два, они не взаимоисключающие и обрабатываются одним и тем же конвейером начиная с шага 2:

- **manual_message** — поставщик, у которого `suppliers.price_channel_id IS NULL`, присылает прайс текстом в служебный чат/ЛС до дедлайна (как раньше, без изменений).
- **channel_post** — поставщик, у которого `suppliers.price_channel_id` заполнен, публикует прайс в своём Telegram-канале; backend забирает новые посты этого канала через API сервиса-парсера (см. 9.5.1). Это устраняет необходимость, чтобы поставщик отдельно дублировал прайс сообщением в бот — достаточно того, что он публикует его в своём канале так, как делал бы это независимо от нашей системы.

```
ВХОД: APScheduler, cron 11:00 МСК (`0 11 * * *`), direct вызов `run_morning_price`.
Окно публикации прайса в каналах поставщиков: 08:00–11:00 МСК. Realtime-listener парсера пишет посты в `tg_parser` сразу; в 11:00 backend забирает все новые текстовые посты добавленных каналов (`suppliers.price_channel_id`) в `raw_prices` и собирает draft.

1a. ДЛЯ suppliers WHERE price_channel_id IS NULL:
      SELECT новые сообщения от этого supplier за окно [прошлый прогон, сейчас),
      помеченные как прайс-лист (см. раздел 12 по способу пометки)
1b. ДЛЯ suppliers WHERE price_channel_id IS NOT NULL:
      posts = parser_client.get_posts(channel_id=price_channel_id,
                                       from_=last_price_sync_at,
                                       content_type='text')   -- 9.5.1
      UPDATE suppliers SET last_price_sync_at = MAX(posts[].post_date)
2. ДЛЯ каждого текста прайса (из 1a или 1b):
     hash = sha256(text)
     source = 'manual_message' | 'channel_post'
     INSERT raw_prices (supplier_id, text, content_hash, source, source_post_id,
                        source_message_link) ON CONFLICT (content_hash) DO NOTHING
     cache = parse_cache WHERE content_hash=hash AND kind='price_list'
     если cache найден → items = cache.result_json
     иначе → items = llm.parse_price_list(text) (8.2) → INSERT INTO parse_cache
     ДЛЯ каждого item:
       sku_key = f"{model}|{storage}|{color}|{region}|{sim}"
       INSERT parsed_items (raw_price_id, sku_key, model, storage, color, region, sim,
                             condition, price, currency)
3. SQL:
     SELECT sku_key, MIN(price) as min_price, ...
     FROM parsed_items
     WHERE raw_price_id IN (сегодняшние raw_prices)
     GROUP BY sku_key
4. ДЛЯ каждого sku_key:
     category = classify(model)  -- iphone_17_pro/iphone/airpods/apple_watch/ipad/macbook/samsung_s26_ultra/samsung/playstation/dyson/*
     rule = markup_rules WHERE category=category AND active=true (fallback: category='*')
     markup = rule.markup_fixed OR clamp(default, rule.markup_min, rule.markup_max)
     our_price = min_price + markup
5. Собрать draft прайса (без supplier, без закупочной цены, без размера наценки — [ТЗ §2]):
     "iPhone 17 256GB Black 🇯🇵 — {our_price} ₽"
6. INSERT price_list_drafts (items=JSON, status='pending')
7. Отправить draft в `PRICE_APPROVAL_CHAT_IDS` **и** в ЛС всех `owners` с `dm_ok=true`. Сообщение содержит inline-кнопки «Утвердить» / «Отклонить» и команды `/approve_price` / `/reject_price` как fallback.
8. При approve (кнопка или команда) → атомарный `UPDATE ... WHERE status='pending'`, `approved_by_telegram_id` = telegram_id нажавшего; `approved_by` = `employees.id` только если нажавший — active employee; публикация в `PRICE_PUBLISH_CHAT_IDS`.
```

Формула наценки: `our_price = min_purchase_price + markup`, `markup` берётся из `markup_rules` (500–1000 ₽ по умолчанию, настраивается вручную) `[ТЗ §2]`.

#### 9.5.1 Интеграция с сервисом парсинга каналов поставщиков

Сервис-парсер (`TG_CHANNEL_PARSER_DOCUMENTATION.md`) — отдельный процесс со своей БД (`tg_parser`) и MTProto-сессией. Бот закупок с ним не делится базой и не хранит MTProto-сессию — единственная точка связи — HTTP API парсера, вызываемый backend'ом бота закупок как обычный внешний сервис:

```
GET {PARSER_API_URL}/posts?channel_id={id}&from={ts}&content_type=text
Headers: Authorization: Bearer {PARSER_API_TOKEN}
```

Парсер должен быть заранее подписан (тем же личным аккаунтом) на канал каждого поставщика с `price_channel_id`, и этот канал в парсере должен быть зарегистрирован с `purpose='supplier_price_source'` — тогда парсер не запускает по этим постам собственную AI-классификацию (она предназначена для канала личного мониторинга, а не для прайсов), а только сохраняет сырой текст и отдаёт его по API. Разбор прайса (`llm.parse_price_list`) выполняет исключительно backend бота закупок — во избежание рассинхронизации схем и дублирования логики между двумя сервисами.

Если поставщик публикует прайс не текстом, а фотографией/файлом (скан прайс-листа) — такой пост не обрабатывается ни парсером, ни ботом закупок: OCR/распознавание изображений не входит в скоуп ни одного из двух сервисов `[раздел 16]`. Это должно быть подтверждено с заказчиком отдельно для каждого поставщика с каналом.

### 9.6 Аналитика владельцу (`report_service.build_report`)

```
ВХОД: "/report [day|week|{request_id}]" от owner (dm_ok=true) ИЛИ cron → POST /jobs/daily-report

1. period_key = f"{date}_{period}"
2. cache = report_cache WHERE period_key=period_key
   если найден и age < TTL → вернуть cache.formatted_text
3. metrics (SQL, без LLM):
   requests_total, deals_closed, avg(price_initial), avg(final_price),
   savings_vs_initial = avg(price_initial) - avg(final_price),
   top_suppliers (COUNT deals GROUP BY supplier),
   open_requests (status NOT IN ('closed','cancelled'))
4. INSERT report_cache (period_key, metrics_json=metrics)
5. formatted = llm.format_report(metrics) (8.4)
   если LLM недоступен → formatted = jinja_fallback(metrics)
6. UPDATE report_cache SET formatted_text=formatted
7. destination = owner.telegram_id (если dm_ok=true) ELSE settings.analytics_chat_id
8. telegram.send_message(destination, formatted, parse_mode='HTML')
```

Поля отчёта строго соответствуют `[ТЗ §7]`: запросы сотрудника, сообщения поставщикам, ответы поставщиков, первоначальная цена, цена после торга, выбранный поставщик, итог сделки — все считаются из `requests`, `messages_out`, `messages_in`, `quotes`, `deals`.

### 11.2 Owner purge — `/purge_request` и `/purge_old`

| Команда | Поведение |
|---|---|
| `/purge_request {id}` | сообщение с inline «Удалить» / «Отмена»; hard-delete только по callback `purge_confirm` |
| Удаляемые таблицы | `messages_out`, `messages_in`, `quotes`, `deals`, `requests` (в одной транзакции, явный `DELETE`) |
| Не трогаем | `update_log`, `suppliers`, `employees`, `parse_cache`, `report_cache` |

## 13. Безопасность и надёжность

1. Whitelist на каждый входящий update: `owners`/`employees`/`suppliers` по `telegram_id`; всё остальное — игнорировать.
2. Идемпотентность на двух уровнях: `update_log.tg_update_id` (весь update) и `UNIQUE(chat_id, tg_message_id)` в `messages_out`/`messages_in` (защита от дублей при повторных webhook).
3. Единый webhook на токен бота — backend принимает Telegram webhook напрямую с `secret_token`.
4. `X-Telegram-Bot-Api-Secret-Token` защищает `/telegram/webhook`; `X-Webhook-Secret` защищает ручные `/jobs/*`.
5. LLM output всегда валидируется по JSON Schema; при ошибке валидации — `confidence=0`, fallback на raw текст сотруднику.
6. Правило "no hallucination": цифры в отчётах и сообщениях поставщикам — только из БД/шаблонов; LLM не подставляет собственные числа.
7. Privacy Mode бота — Enabled, чтобы не обрабатывать вообще все сообщения клиентов в группах.
8. Все отправленные и полученные сообщения логируются в БД без исключений — это единственный источник для п.7 ТЗ (аналитика/контроль).

## 15. Критерии приёмки (сквозные тест-кейсы)

1. Сотрудник делает reply на сообщение клиента и пишет `/ask` → все `active=true` поставщики получают сообщение с `#N`.
2. Поставщик отвечает reply на сообщение с `#N` → ответ появляется в исходной группе с меткой поставщика; `messages_in` содержит запись.
3. Пользователь не из `employees` пишет `/ask` в группе → команда игнорируется, никакой рассылки не происходит.
4. Владелец после `/start` вызывает `/report day` → получает сообщение с цифрами, совпадающими с прямым SQL-запросом к БД.
5. Повторная доставка одного и того же Telegram update (повтор webhook) не создаёт вторую рассылку поставщикам (проверка `update_log`).
6. При недоступном LLM: маршрутизация `/ask`→поставщики→группа продолжает работать; `/report` отдаёт fallback-текст без ошибки 500.
7. Ответ поставщика с ценой в свободной форме и низким `confidence` не попадает в `quotes.price_initial`, но `raw_text` виден сотруднику с пометкой «неуверенное распознавание».
8. Наценка меняется в `markup_rules` без деплоя кода — на следующем прогоне `/jobs/morning-price` применяется новое значение.
9. У поставщика с заполненным `price_channel_id` появляется новый пост с ценами в его Telegram-канале — без каких-либо действий со стороны сотрудника или поставщика следующий забор `/jobs/morning-price` создаёт соответствующую запись в `raw_prices` с `source='channel_post'`.
10. Владелец вызывает `/purge_request {id}` → получает запрос подтверждения; после «Удалить» строки `requests`, `quotes`, `deals`, `messages_in`, `messages_out` для этой заявки отсутствуют; повторное подтверждение → «не найдена»; сотрудник `/purge_request` → `ignored`.
11. Владелец `/purge_old 30` без `--confirm` → dry-run с перечнем ID; с `--confirm` → удалены только `cancelled`/`closed` старше 30 дней.
12. Owner через `/menu` → **Сотрудники** добавляет менеджера по `telegram_id` → этот пользователь в клиентской группе вызывает `/ask` → заявка создаётся; чужой `telegram_id` — игнор.

## 16. Явно вне скоупа документа/MVP

- Userbot (Telethon/Pyrogram) — не используется внутри самого бота закупок; весь бот работает только через Bot API. MTProto/userbot живёт исключительно в отдельном сервисе-парсере (`TG_CHANNEL_PARSER_DOCUMENTATION.md`), и бот закупок обращается к нему только через HTTP API (9.5.1), не имея собственной MTProto-сессии.
- Приём прайсов в виде файлов/фото/Excel — не входит, пока не согласовано отдельно (ТЗ описывает только текстовый ввод `[ТЗ §1]`) — это ограничение сохраняется и для прайсов, пришедших из канала поставщика (см. 9.5.1).
- Автоматическое согласие на сделку или смену модели/цвета ботом — запрещено `[ТЗ §5]`.
- Telegram Business / Chat Automation — не используется в MVP; рассматривается только как возможное расширение для ЛС-диалога с клиентом отдельно от группового бота.

## 18. Данные, которые понадобятся от вас (бот закупок)

1. `TELEGRAM_BOT_TOKEN` — токен бота, выдаётся [@BotFather](https://core.telegram.org/bots/features#creating-a-new-bot) при создании бота.
2. `ADMIN_ALERT_CHAT_ID` — chat_id, куда слать алерты при сбоях backend/парсера.
3. `ANALYTICS_CHAT_ID` — chat_id, куда слать ежедневный/еженедельный отчёт владельцу.
4. Список `telegram_id` владельцев (`owners`) — кто имеет право на `/report`, `/stats` и `/menu` (раздел 5). Первичное добавление owner — через SQL; далее self-service в боте.
5. Сотрудники (`employees`) — owner заводит через `/menu` → **Сотрудники** (раздел 11.1): имя + `telegram_id`. SQL нужен только для bootstrap или экстренного восстановления.
6. Список поставщиков (`suppliers`): имя, подтверждение, что каждый сделает `/start` боту, и для тех, у кого есть свой Telegram-канал с ценами — его `@username`/`channel_id` (пересекается с `TG_CHANNEL_PARSER_DOCUMENTATION.md`, раздел 16, п.3a).
7. Chat_id каждой клиентской группы, где сотрудники будут вызывать `/ask` (бот должен быть добавлен в каждую заранее).
8. Конкретные значения наценки для `markup_rules` (процент или сумма, возможно разные для разных категорий товара).
9. Провайдер и модель LLM (`LLM_PROVIDER`, `LLM_MODEL`, `LLM_API_KEY`) — локальный Ollama или внешний API.
10. Подтверждение или изменение `CONFIDENCE_THRESHOLD` (по умолчанию 0.75) — порог для автоматического принятия расчёта LLM.
11. Подтверждение окна recheck (2–5 часов по `[ТЗ §6]`) — точные границы, если нужно изменить.
12. `DATABASE_URL` — где разворачивается PostgreSQL (свой сервер или управляемый сервис, например Supabase).
13. `WEBHOOK_SECRET`, `TELEGRAM_WEBHOOK_SECRET_TOKEN` и `PUBLIC_BACKEND_URL` — сгенерировать или согласовать.
14. Фактический часовой пояс сервера — в примере указан Europe/Moscow, подтвердить, что это верно.
15. Всё, перечисленное в `TG_CHANNEL_PARSER_DOCUMENTATION.md`, раздел 16 (api_id/api_hash личного аккаунта, номер телефона для авторизации, подтверждение членства аккаунта в каждом канале и т.д.) — отдельный сервис, но без этих данных интеграция с каналами поставщиков (§9.5.1) работать не будет.
