# Jev runbook

Jev (TypeSafe System One) классифицирует ответ поставщика: это цена или нет, и к какому кандидату из уже загруженного списка она относится. Цену считает `price_parse`. Котировку пишет `quote_service`. Сделку Jev не создаёт.

## Что можно

- Спросить TypeSafe, является ли текст коммерческой ценой (`is_price` noul).
- Спросить, называет ли текст ту же модель, что любая заявка в списке (`matches_listed_order` noul). Порог в коде: ≤ 0.3 нет, ≥ 0.7 да, между ними разбор человеком.
- Спросить, какой opaque id из переданного списка кандидатов подходит (`choice`), либо `none` / `ambiguous`.
- В shadow записать решение и сравнить его с детерминированным путём и подтверждением сотрудника.

## Что нельзя

Считать цену, наценку, лучшую котировку, выбирать поставщика сделки, создавать quote/deal, менять статус заявки, писать сырой ответ провайдера в бизнес-таблицы, генерировать текст поставщику, показывать конкурентные цены, привязывать id вне списка кандидатов.

## Поток

Входящее сообщение → проверка маршрута → детерминированная привязка (reply, явный id, SKU/attrs) → опционально Jev → пороги в коде → существующий парсер цены → quote или карточка сотруднику.

Webhook работает асинхронно (`WEBHOOK_ASYNC_ENABLED=true`, `OUTBOX_DELIVERY_ENABLED=true`): обновление сразу ACK и попадает в `webhook_inbox`, обработку (включая вызовы Jev) выполняет `backend-worker`. Латентность Jev не блокирует ACK. Дедупликация (`insert_message_in_idempotent`) выполняется до привязки и до любых AI-вызовов: повторное/дублирующее обновление выходит без обращений к провайдеру. Кандидаты загружаются один раз на сообщение и передаются по всей цепочке.

Если в тексте есть модель (линейка, поколение, вариант или SKU), а среди открытых заявок этого поставщика нет той же модели, сообщение игнорируется: карточки «К какой заявке отнести?» нет. Правило общее: другое поколение, другой вариант (Pro и обычная, Pro и Pro Max) или другая линейка (iPhone и iPad, iPhone и Samsung). Это делает код, даже когда Jev выключен или в shadow. Jev дополнительно отвечает noul `matches_listed_order`: вероятность ≤ 0.3 или уверенный `binding=none` тоже дают ignore. Конфликт только цвета, памяти, SIM или региона остаётся на разборе у сотрудника.

`not_price` игнорируется только если вероятность цены (`is_price` noul) не выше `1 - JEV_PRICE_THRESHOLD`. `binding_confidence` для этого решения не используется: это концентрация Choice по кандидатам, а не уверенность, что текста цены нет. Иначе сообщение остаётся в разборе. Исходный текст не удаляется.

## Стадии

0. `JEV_ENABLED=false`. Код задеплоен, вызовов нет. Перед стадией 1 база должна быть на миграции не ниже `0027_supplier_ai_decisions`. Текущий head процесса — `0029_jev_decision_tokens` (`alembic upgrade head` из `backend/`). Таблица `supplier_ai_decisions` создаётся миграцией `0027`; миграция `0029` добавляет `input_tokens`, `output_tokens`, `from_cache` для учёта стоимости и cache-hit rate.
1. `JEV_ENABLED=true` и `JEV_SHADOW_MODE=true`. Решение пишется в `supplier_ai_decisions`, поведение продакшена не меняется.
2. `JEV_SHADOW_MODE=false` только после разбора shadow. Автопривязка возможна при одной совместимой позиции, без конфликта атрибутов и при цене, которую принял существующий парсер.
3. Несколько кандидатов в auto-bind — только после отдельного порога ложных привязок, который утверждает владелец. Сейчас голая цена при нескольких кандидатах всегда `multiple_candidates_bare_price`.
4. Следить за правками сотрудников. При росте ложных привязок вернуть shadow или выключить Jev. Circuit breaker (ниже) защищает только от сбоев провайдера, а не от ложных привязок — этот контроль остаётся ручным.

## Circuit breaker

После `JEV_BREAKER_FAILURE_STREAK` (по умолчанию 5) подряд ошибок провайдера breaker открывается: вызовы Jev мгновенно уходят в fallback с reason `jev_breaker_open`, HTTP не выполняется. Раз в `JEV_BREAKER_COOLDOWN_SECONDS` (по умолчанию 60) допускается один half-open пробный запрос; успех закрывает breaker, неудача снова открывает. Открытие и повторное открытие дают admin-алерт и инкремент `jev_breaker_trips_total`; закрытие — только алерт. Состояние видно в `jev_health_snapshot()` (`breaker`). Если внутри одного многострочного ответа чанк открыл breaker, остальные чанки этого сообщения в HTTP не идут.

Breaker дополняет, а не заменяет kill switch `JEV_ENABLED=false`: при ложных привязках или инциденте по-прежнему выключать через `JEV_ENABLED`. Строки fallback с `jev_breaker_open` записываются с `error_code` и не попадают в кэш решений.

## Многострочные ответы (fan-out)

Для многострочных ответов после детерминированного матча по каждой строке оставшиеся строки уходят одним batch-запросом `/v1/systemone` (state с общими кандидатами платится один раз, вопросы по строкам выполняются параллельно). Чанки не больше `JEV_BATCH_MAX_LINES` (по умолчанию 15) строк; сверх лимита — несколько batch-вызовов. Конкурентность HTTP на процесс ограничена `JEV_MAX_CONCURRENCY` (по умолчанию 3). Промпты версии `supplier-classify-v5`: смена версии инвалидирует кэш решений by design. Токены batch-запроса пишутся в лог `jev_batch_usage` на запрос целиком; построчные `input_tokens`/`output_tokens` для batch остаются NULL (деление токенов по строкам не выдумывается).

## Аварийное выключение

`JEV_ENABLED=false`, перезапуск процессов backend. Откат кода не нужен. Уже созданные котировки эта операция не удаляет.

## Секреты

`JEV_API_KEY` только в secret store. Ротация: новый ключ в кабинете TypeSafe, замена env, рестарт, отзыв старого ключа.

## Отчёт shadow

Из каталога `backend/`:

```bash
python -m scripts.jev_shadow_report
```

Если нет подтверждений сотрудников, отчёт прямо говорит, что precision/recall не считаются. Не подставлять оценки вручную.

Отчёт также показывает: распределение `reason_code` (какая корзина разбора доминирует: `jev_low_margin`, `jev_model_uncertain`, `multiple_candidates_bare_price`, …), суммы `input_tokens`/`output_tokens` и cache-hit rate (`from_cache` среди успешных строк). Пороги 0.95/0.95/0.20 менять только по данным shadow, не подгонять под отдельные кейсы.

Приемлемый порог ложной автопривязки для стадии 3 владелец фиксирует здесь числом до включения. Пока число не утверждено, стадия 3 запрещена.
