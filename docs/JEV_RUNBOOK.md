# Jev runbook

Jev (TypeSafe System One) классифицирует ответ поставщика: это цена или нет, и к какому кандидату из уже загруженного списка она относится. Цену считает `price_parse`. Котировку пишет `quote_service`. Сделку Jev не создаёт.

## Что можно

- Спросить TypeSafe, является ли текст коммерческой ценой (`noul`).
- Спросить, какой opaque id из переданного списка кандидатов подходит (`choice`), либо `none` / `ambiguous`.
- В shadow записать решение и сравнить его с детерминированным путём и подтверждением сотрудника.

## Что нельзя

Считать цену, наценку, лучшую котировку, выбирать поставщика сделки, создавать quote/deal, менять статус заявки, писать сырой ответ провайдера в бизнес-таблицы, генерировать текст поставщику, показывать конкурентные цены, привязывать id вне списка кандидатов.

## Поток

Входящее сообщение → проверка маршрута → детерминированная привязка (reply, явный id, SKU/attrs) → опционально Jev → пороги в коде → существующий парсер цены → quote или карточка сотруднику.

`not_price` игнорируется только если вероятность цены (`is_price` noul) не выше `1 - JEV_PRICE_THRESHOLD`. `binding_confidence` для этого решения не используется: это концентрация Choice по кандидатам, а не уверенность, что текста цены нет. Иначе сообщение остаётся в разборе. Исходный текст не удаляется.

## Стадии

0. `JEV_ENABLED=false`. Код задеплоен, вызовов нет. Перед стадией 1 база должна быть на миграции не ниже `0027_supplier_ai_decisions`. Текущий head процесса — `0028_price_publication` (`alembic upgrade head` из `backend/`). Таблица `supplier_ai_decisions` создаётся миграцией `0027`.
1. `JEV_ENABLED=true` и `JEV_SHADOW_MODE=true`. Решение пишется в `supplier_ai_decisions`, поведение продакшена не меняется.
2. `JEV_SHADOW_MODE=false` только после разбора shadow. Автопривязка возможна при одной совместимой позиции, без конфликта атрибутов и при цене, которую принял существующий парсер.
3. Несколько кандидатов в auto-bind — только после отдельного порога ложных привязок, который утверждает владелец. Сейчас голая цена при нескольких кандидатах всегда `multiple_candidates_bare_price`.
4. Следить за правками сотрудников. При росте ложных привязок вернуть shadow или выключить Jev. Автоматического выключателя в этом релизе нет.

## Аварийное выключение

`JEV_ENABLED=false`, перезапуск процессов backend. Откат кода не нужен. Уже созданные котировки эта операция не удаляет.

## Секреты

`JEV_API_KEY` только в secret store. Ротация: новый ключ в кабинете TypeSafe, замена env, рестарт, отзыв старого ключа.

## Отчёт shadow

Из каталога `backend/`:

```bash
python -m scripts.jev_shadow_report
```

Если нет подтверждений сотрудников, отчёт прямо говорит, что precision/recall не считаются. Не подставлять оценки вручную.

Приемлемый порог ложной автопривязки для стадии 3 владелец фиксирует здесь числом до включения. Пока число не утверждено, стадия 3 запрещена.

## Staging smoke

```bash
JEV_STAGING=1 JEV_API_KEY=... pytest tests/staging/test_jev_real_api.py -q
```

Обычный CI этот тест не гоняет без маркера и ключа: тест сам вызывает `pytest.skip`.

## Открытый риск вендора

Срок хранения и регион обработки TypeSafe в публичной документации не указаны. Zero data retention — через sales@typesafe.ai. До ответа вендора стадия 2 в проде не включается.
