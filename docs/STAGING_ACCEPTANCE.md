# Staging acceptance

**Обязательный гейт перед релизом (C3):** релиз в prod запрещён без живого прогона этого чеклиста на staging и сохранённых доказательств (шаблон: `docs/staging-evidence-template.md`). Полный pytest с Postgres (dockerized-команда — в `СЕРВИСЫ.md`, раздел «Dockerized полный pytest») прогоняется до acceptance; без БД локально проходят только стаб/юнит-тесты (CI-001).

Живой прогон делает оператор. Не использовать production-чаты, production-поставщиков, production-базы и production-секреты.

## Что уже гоняется в CI

- `backend/tests/acceptance/` — Postgres, фейковые Telegram, LLM и parser.
- `tg-channel-parser/tests/acceptance/` — API parser, когда задан `PARSER_TEST_DATABASE_URL`.

Userbot, реальный Telegram и публикация в чат в CI не ходят.

## Команды

Backend, из `backend/`:

```bash
uv run pytest tests/acceptance -q
```

Parser, из `tg-channel-parser/`, с тестовой БД:

```bash
PARSER_TEST_DATABASE_URL=postgresql+asyncpg://tg_parser:tg_parser@localhost:5432/tg_parser_test \
  uv run pytest tests/acceptance -q
```

## Что обязан сохранить оператор

- SHA коммита.
- `alembic current` для `zakupki` и `tg_parser`.
- Идентификатор прогона.
- `request_id`, `draft_id`, id канала parser.
- Ожидаемый и фактический статус.
- Логи без токенов, session string и текстов сообщений клиентов.
- Точные команды.
- Конфиг окружения без секретов.

## Сценарии, которые CI не закрывает

Нужны тестовый бот, тестовый аккаунт Business и тестовый канал:

1. `/ask` в тестовой группе и ответ поставщика в Telegram.
2. Пост в канале, который читает userbot, затем morning-price с `degraded=0`.
3. Одобрение черновика публикует прайс один раз.
4. Повтор того же job не создаёт второй черновик.
5. Остановка worker через `SIGTERM` и повторный claim после истечения lease.

Ожидание morning-price на здоровом прогоне: `degraded=0`. Если parser или LLM недоступны, HTTP-процесс остаётся живым, а результат помечается degraded.

## Регрессии итерации аудита (A/B/C)

6. **B1 — edit/delete прайс-поста:** поставщик редактирует пост в канале → `parser_posts.raw_text` обновлён, `edited_at` заполнен, `post_date` не изменился; morning-price перечитывает цену (parse_cache ключуется по контенту). Удаление поста → `excluded=true`, пост не попадает в `GET /posts` и в прайс.
7. **A3 — мультипозиционный `/ask` (10+ позиций):** клиент сразу получает «Заявка принята, позиций: N»; нормализация и рассылка идут в worker (async-режим), webhook не превышает таймаут Telegram.
8. **A2 — потеря обновления:** в sync-режиме смоделировать ошибку обработки (например, недоступный parser при `/ask`) → обновление попадает в `webhook_inbox`, повторяется воркером; после `WORKER_MAX_ATTEMPTS` — `dead` и видно в «Ошибки системы». В async-режиме проверить идемпотентность повторной доставки того же `update_id`.
9. **A5 — ноль доставок RFQ:** все поставщики недоступны → заявка переходит в `needs_recheck`, в группе карточка с кнопкой «Повторить рассылку»; повтор после восстановления поставщика переводит заявку в `awaiting_answers`. В outbox-режиме отложенная доставка (`pending`) не считается нулём.
10. **B4 — backfill после resolve:** канал резолвится, но история недоступна → создаётся задача `backfill_channel`, воркер повторяет с backoff; после успеха история в `parser_posts`.
11. **OPS-012 — удалить и восстановить канал:** `/menu` → «Каналы прайсов» → добавить канал → ✅ → «Удалить» (🗑) → «Восстановить» → снова ⏳ затем ✅ → новый пост в канале попадает в `parser_posts` и в morning-price (`degraded=0`). Привязка к поставщику в 🗑 недоступна.
12. **C1/C2 — деградация доставки:** при стабильно падающей доставке heartbeat `worker` не обновляется (`/ready` → 503), операторам приходит алерт каждые 5 ошибок подряд; `/health/details` показывает блок `llm` с `configured`.
13. **Прайс не молчит (`/menu` → «Парсер»):** публикация текстового поста в канале поставщика → следующий **cron** даёт `raw_prices > 0` и черновик с наценкой; если черновика нет — в чат операторов и владельцам приходит `[ALERT] Утренний прайс не собран` с конкретной причиной. Вкладка «Цены» показывает только сегодняшние позиции (`47 000 ₽`) и номер страницы, без черновика и без причин. Вкладка «Каналы и статус» — ✅/⏳/❌ канала, привязку к поставщику и `last_price_sync_at`. Кнопка «▶ Запустить прайс» забирает **3 последние** сообщения канала, один LLM-разбор склейки, черновик без наценки; при занятом локе — «уже выполняется»; тестовый прайс должен быть **одним из последних трёх** постов в канале. Проверить отдельно пустой `PARSER_API_TOKEN` (`parser_token_missing`) и неверный порт (`parser_unreachable`).

## A4 — bind-ask на staging (решение о prod — по результатам)

На staging включить `SUPPLIER_BIND_ASK_ENABLED=true` (в prod дефолт `false` сохраняется до решения владельца):

1. Поставщик отправляет «голую» цену без reply на RFQ → бот задаёт уточняющий вопрос «к какой заявке эта цена?».
2. Ответ поставщика привязывает цену → котировка записана → цена публикуется клиенту по правилам автопубликации.
3. Замерить долю pending до/после: телеметрия `record_supplier_binding_pending` и `messages_in.bind_status` по заявкам (OPS-009 — основная жалоба «цены в боте»).
4. Решение о включении в prod принимает владелец по доле pending и качеству привязки; зафиксировать в `ИЗВЕСТНЫЕ_ПРОБЛЕМЫ.md` (OPS-009).

## A6 — поштучные цены пакетной заявки (OPS-011)

Текущее поведение принято: при `AUTO_PUBLISH_FIRST_VALID_PRICE=false` поштучные цены пакетной заявки в чат не уходят — только сводный прайс кнопкой «Опубликовать». Улучшение UX (сводка поштучных цен одним сообщением после `QUOTE_COLLECTION_WINDOW_MINUTES`) требует явного решения владельца о формате; до решения поведение не меняется. Зафиксировано в `ИЗВЕСТНЫЕ_ПРОБЛЕМЫ.md` (OPS-011).
